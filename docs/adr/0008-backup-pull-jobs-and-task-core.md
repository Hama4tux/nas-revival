# ADR 0008: Backup pull jobs and the shared task core

- Status: accepted (2026-11-26; phase 1 built in W4.3)
- Scope: BKP-10/11 (web roadmap W4.3) as a task type on the scheduler core of TASK-01..03 (W3.3)
- Context: an interim pull job already runs on the NAS outside NAS Revival: a systemd timer starts a
  script as a dedicated system user, which pulls `/var/backups` of several servers with rsync over SSH
  (NAS-owned key; on each server the key is pinned to the NAS address and forced to
  `rrsync -ro <dir>`), mirrors them into `<root>/apps/<job>/` and makes a daily hardlink version
  `<root>/versions/<date>/` (`cp -al`), keeping a fixed number of days. It writes a JSON status and
  fails when the server-side marker file is older than a limit. NAS Revival does not show it, and only
  power preflight knows about it (`backup_running`).

## Decision

- **Order (owner, 2026-11-26):** the scheduler (W3.3) comes first and is the task core; backup jobs
  (W4.3) add the task type `backup-pull` on it. The paragraph "Task core" describes the state built in W3.3
  (2026-11-26).
- **Task core (built in W3.3):** `/etc/nas-revival/tasks.json` (fixed types `smart`, `recycle-cleanup`;
  `backup-pull` comes with W4.3) is validated and written by the helper (`task.get/set/run/stop`), which
  renders one `nas-revival-task-<id>.timer` per task for the static template `nas-revival-task@.service`
  and reconciles the timers at start. The runner `nas-revival task run <id>` runs as `nas-revival`
  (no capabilities, `SupplementaryGroups=nas-heavy`) and does the work through existing helper ops.
  One heavy-task lock `/run/lock/nas-heavy.lock` (flock for the whole run, waits up to 3 h, then the run
  is recorded as skipped; tmpfiles `f`+`z` `0660 root:nas-heavy` – root-owned because of
  `fs.protected_regular`; runners open it without O_CREAT), shared with the interim pull job; power
  preflight probes it (`task_running`). History: `/var/lib/nas-revival/task-history.json`, last 30 runs
  per task (start, end, result ok/failed/skipped/stopped, short message); W4.3 adds bytes for backups.
  No free-form command task type (TASK-02).
- **Backup job type "pull over SSH"** (validated fields only): name, host (IP or hostname), user,
  remote paths (relative, no `..`), daily or weekly time, version retention days (required,
  1–90), optional freshness marker file and maximum age, optional bandwidth limit and excludes.
  Mode "mirror + versions": `--delete` applies to the mirror only, the versions keep what was
  deleted; the UI explains this before the job is saved (FEATURE_MATRIX BKP-10 rule).
- **Storage root** *(amended 2026-11-27: the destination is a `backupTarget` share)*: the original design kept
  pulled backups under one reserved root on the data volume (`/srv/data/apps`, `/srv/data/versions`), owned by the
  backup user, mode 0700, never offered as an SMB/NFS share and refused as a share path. Superseded: the destination
  is a normal shared folder with the property `backupTarget` (read-only for everybody, `nas-backup` the only writer
  through an ACL entry, not exportable over NFS, on `/srv/data`); the hidden pseudo share `zalohy`, the reserved names
  and `backup.share.get/set` are gone. Task destinations and the layout inside the share follow in later steps; until
  then the jobs still write to the old paths. Original text: Restore access comes through the web UI (list versions
  and files first, download and restore-to-share with File Station W4.1). Restore-to-share (phase 2b): the helper
  copies a folder or file of a version into a share the admin's own account may write to, in the background
  under a hidden name, never overwriting, owned by the admin like a File Station upload, symlinks skipped.
- **Runner privileges:** the job runs as the unprivileged backup user in a systemd sandbox with one
  `ReadWritePaths` entry for the data volume root (separate bind mounts break hardlinks, EXDEV),
  `Nice`, idle I/O class; one job at a time through the heavy lock (240 MB RAM).
- **Key:** one ed25519 key of the NAS, generated by the helper (`backup.key.generate`); the UI shows
  only the public key and a ready `authorized_keys` line with `from="<NAS address>",restrict,
  command="rrsync -ro <dir>"`. The private key is never shown, exported or included in a config export.
- **Host key:** `backup.host.scan` shows the fingerprint, the admin confirms it (with a hint how to
  read it on the server or hypervisor); a changed key fails the job with a clear error until it is
  confirmed again.
- **Connection test:** list the remote path (`--list-only`), then check the restriction: when the key
  gets a shell or may write, the UI warns that the key has full access.
- **Status:** last result and age on the dashboard (BKP-11), failed or stale job as a red badge;
  notifications with W4.5.
- **Migration of the interim job:** import its jobs file into `tasks.json`, keep its key, known hosts
  and directories, start the new timer, disable the old timer. Nothing changes on the servers.

## Consequences

- The web process can define jobs only within validated fields; the root helper renders units and
  keys, the runner is not root.
- Versions are cheap for unchanged files but every changed dump is a full copy; the dashboard shows
  used space of the backup root.
- Open: memory of rsync with large file trees on 240 MB RAM must be measured before enabling
  jobs with tens of thousands of files.
